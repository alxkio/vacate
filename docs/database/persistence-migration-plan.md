## Mapping proposal

Use internal Infrastructure persistence row types and Fluent IEntityTypeConfiguration mappings, with explicit hydration methods/factories reviewed for each domain aggregate. Keep EF attributes/navigation proxies out of Domain. Map User name as scalar row columns and Family into required UserPrivateProfile row; load privately only for authorized own-profile use cases. Never serialize tracked entities. Department/team rows belong to Organization hydration, with CompanyId explicitly populated even though the domain child lacks that property. Map MembershipConfiguration scalar fields; SettingsRole has an explicit stable string converter. Map VacationSettings scalar bits/legacy years. After the explicit 2026-11-02 amendment, AnnualBalance is a read projection over MembershipEntitlements and Leaves; used/pending/available are derived, never stored totals. See [the replacement and guarded forward migration](derived-leave-balances.md).

Immutable public Guid and CreatedAt cannot be marked modified. Map lifecycle private setters through explicit row conversion; preserve deleted history. A scoped identity map ensures the same aggregate instance is returned within a unit of work. SaveChanges translates tracked domain changes to rows once; error abort disposes the context so mutated objects cannot leak into a later request. Each owner and dependent concurrency token is retained in a private tracking envelope, not a new HTTP field. Root token advances when structure changes; use token predicate on root even if only child changed. All queries start from authorized actor/company scope; query filters cannot replace AccessPolicy.

Use int SQL SEQUENCE per numeric key space with NO CYCLE (positive values), rather than MAX+1 or IDENTITY incompatible with constructors requiring positive Id. I*Repository.NextId reads NEXT VALUE FOR in the transaction; gaps are acceptable and IDs stay private. Preserve existing system-role IDs/GUIDs, seeded reference IDs and public GUIDs. Before importing fixture IDs, start sequences above max imported values under exclusive migration control. Do not reseed live sequences backward. Role/catalogue GUIDs must not be regenerated on each startup.

Current synchronous ports can be mapped synchronously for the bounded adapter; an async port change needs explicit call-chain review, not sync-over-async. IUnitOfWork.Execute owns a real transaction, company/account locking protocol, rowversion check and one SaveChanges; nested calls share it and cannot commit early. Existing repository All() access must be reviewed for company/private projection and bounded queries; future typed query ports can narrow reads without moving authorization into endpoints. No mediator or generic repository abstraction is needed.

Keep ISessionStore/ICredentialValidator separate from resources. Never persist demo passwords or raw bearer tokens through EF. The [2026-11-13 ADR-0004 amendment](../adr/0004-relational-persistence.md#product-lead-amendment--shared-sessions--2026-11-13) accepts hashed, account-keyed shared session rows in SqlServer mode under the existing VAC-42 refinement subtask; InMemory remains process-local. Deployment of empty SQL grants neither app access nor production authentication. Production identity remains separate VAC-27 scope. IProvisioningAccess and IUserPresentationCatalog require explicit compatibility-adapter choice before VAC-26 is ready; they must not silently become platform authority.

## Ordered migration and release plan

1. ADR-0004 architectural acceptance was recorded by the product lead on 2026-11-02. Complete remaining Stage A subset/implementation-gate review: calendar/policy references, fractional service representability, dev marker/presentation compatibility, connection principal and recovery. No migration follows merely from completing a design issue.
2. Provision empty SQL separately through VAC-34. It has no schema-design dependency and grants no runtime/schema authorization. Its free-offer cost gates remain mandatory; no paid restore/test copy is authorized here.
3. Under VAC-26, add scoped adapters/mappings/sequence allocations and reviewed baseline migration for Stage A only. Snapshot generated SQL and constraints; no startup Database.Migrate, EnsureCreated or automatic seeding on application request. Migration runner has explicit least-privilege deployment authority distinct from runtime principal.
4. Build/test in isolated authorized SQL target with V01–V11/V17/V18. Exercise actual SQL provider, two connections for races, rollback injection and API/browser contracts. Do not claim the existing in-memory integration tests cover SQL.
5. Inventory existing state: in-memory state disappears on restart and is not an exportable durable source of truth. Decide whether to discard fictional demo state or export an explicitly consented synthetic snapshot before cutover. No real employee data import inferred. Reproducible fixtures remain Infrastructure/Seeds, opt-in per environment. Preserve all twelve fixture accounts, catalogue GUIDs, lifecycle instants, structure and role references. Do not automatically copy sessions/passwords.
6. Import only approved snapshot into an empty baseline transaction, validate normalization, duplicates, active memberships, all FK targets, decimal representability, UTC and row counts. Abort without partial data on failures; never round PriorService or fabricate policy/ledger history. Initialize sequences after IDs. Repeat seed/import with a stable import ID is idempotent and cannot duplicate accounts.
7. Deploy adapters with controlled persistence-mode configuration, securely resolving an approved managed identity/Entra principal. No connection secrets in repo, no TrustServerCertificate bypass. SQL-only deployment does not change Function App settings. Verify scoped privileges, encryption/TLS and approved narrow network route separately before enabling API use.
8. Stop writes during single cutover, apply reviewed migration once, switch resource mode, run V18 and paired API/browser acceptance against exact deployed revision. No dual-write scheme. Retain known-good deployment and synthetic export until recovery reviewed; absent durable export, a memory rollback loses writes and must be stated.
9. Document named revision/target and tested rollback/recovery limits before release. Use forward corrective migrations for data-bearing changes; never automatically drop tables or run destructive Down in production.

## Allowance, history and legacy compatibility

Stage A preserves CustomAllocation/PolicyMinimum inputs and derives Used/Pending from Leaves. Known fictional legacy consumption becomes explicitly labeled opening entries without occurrence dates, not a reconstructed request ledger. Stage B adds AnnualAllowanceOverrideDays only under VAC-30, after reviewing the stale-override incompatibility in current AnnualBalance. Option proposed: map a trusted existing custom allocation to override only when provenance establishes employer choice; otherwise preserve compatibility snapshot and mark unknown for review, rather than invent an override from calculated policy. Null remains null. Historic yearly rows cannot be reconstructed from today's policy or a free-text version label. Approved historical imports need source version, evaluated inputs and cutoff provenance; missing results stay unknown.

Legacy CarryoverEnabled/CarryoverYears round-trip unchanged under VAC-26. New end-March/configurable cutoff processing belongs to VAC-32. Options for a later accepted migration: retain legacy read-only configuration until explicit opt-in to a new effective-dated policy, or run a reviewed per-company conversion with old/new settings and approved cutoff timezone. Neither 0 nor a positive year count translates automatically into a March deadline; do not delete existing settings, expire balances or perform transfer/write-off during baseline migration.

## Recovery and operational constraints

Before any real-data use, agree RPO/RTO, retention, erasure, backup access and restore procedure with product/privacy owners. Seven-day free-offer PITR retention is not a tested recovery guarantee. Current Microsoft free-tier FAQ says restoring/copying into a free-tier database is unsupported; a recovery operation can require a paid target. VAC-34 zero-cost authorization never authorizes that paid target. For this empty development DB no application recovery service is promised. Later authorized synthetic logical export/import into a new eligible free database may be evaluated, but is not a validated equivalent to PITR and must not use chargeable storage by default.

Do not enable LTR, geo backups/replicas, Defender, private endpoints or monitoring ingestion to complete a recovery checklist. Any paid recovery requirement conflicts with the current zero-cost task and must be separately decided before application cutover.
