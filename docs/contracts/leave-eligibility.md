# Leave eligibility boundary — proposed v1

**Mock contract, 2026-10-24.** The founder wants business decisions owned by the backend later and explicitly requested frontend gender/marital profile checks now. `VacateEligibility` centralizes the provisional mock checks and returns a backend-shaped response; UI components consume those decisions without inferring profile facts from names or roles. The [review matrix](../product/leave-eligibility-review.md) records the exact authorized mock rules and the remaining source conflicts; it does not establish a reviewed statutory rule pack.

Proposed `GET /api/me/leave-eligibility?asOf=YYYY-MM-DD` returns the [JSON schema](leave-eligibility.schema.json). This endpoint is **not implemented**. The server must derive company/employee from authenticated context; the browser does not supply an authoritative employee/company ID. Response IDs allow the client to reject mismatched cached responses, not to grant access. Use one decision per type ID; schema `uniqueItems` does not alone enforce that semantic invariant.

| Field | Purpose |
|---|---|
| `schemaVersion` | Response format version, separate from policy version. |
| `companyId`, `employeeId` | Own-context binding; never infer from a selected calendar colleague. |
| `countryCode` | Employer/company policy country; shared GR configuration for all companies for now, not the person's nationality. Unsupported countries remain To confirm. |
| `asOf`, `evaluationId`, `policyVersion` | Decision context and auditable policy snapshot. Re-evaluate when facts, dates or policy change. |
| `decisions[].typeId` | Existing catalogue ID; the child-illness label retains `dependent-illness`. |
| `status` | `eligible`, `not-eligible`, `to-confirm`; denied and unknown are distinct. |
| `reasonCode`, `reason` | Short, personal display explanation without diagnosis, evidence files or raw family details. |

Eligibility and allowance are separate. Eligible means the current mock checks allow applying; it does not automatically grant a quota or confirm supporting evidence. Unknown/denied decisions suppress personal balance/projection numbers; catalogue allowance/source text remains accessible as reference. Unknown types can preview only in this fictional demo. Denied types are omitted from default personal choices; Show all exposes their reference rules with disabled actions and a preview guard. Frontend filtering is not server enforcement.

**Current country boundary:** `GR-demo-profile-v1` is a single provisional Greece configuration shared by all companies. Company-specific customization is deferred; no company override editor or persisted override table is introduced. Current facts allow or block applying; an upcoming marriage/birth event is not required to display a type. Birth registration and supporting-document uploads are later work. The fixture uses explicit gender/marital/child/sole-care values only for fictional personas, stores them outside shared people/availability projections, and returns decisions rather than raw profile facts.

**Future backend responsibilities:** reviewed/versioned country policy as the baseline for every company, effective dates, qualifying relationships and request context, evidence references, service history, shared-parent consumption and explicit overrides/audit. Later company customization must be layered explicitly on that baseline with precedence and mandatory-country constraints decided; it is not active today. Evidence is private and separately authorized; it is not embedded in the UI response. Event/care identifiers should be opaque. The server calculates eligibility and quantity on submit, rechecks authorization and current policy, rejects or routes unresolved cases according to an approved rule, and reserves balance atomically. A submitted `evaluationId` is audit context, never permission to reuse an old decision.

**Not yet specified:** whether the eventual endpoint also accepts a requested period/type/event context, how expired decisions refresh, the review path for unknown eligibility, policy override permissions and retention. No production profile/evidence tables, migrations or real statutory rules are created here.

**Synthetic examples:** all 12 employees have eligible annual allocation. Explicit mock profile values make Maya married/woman/parent: marriage and paternity are unavailable, maternity is allowed to apply, and existing carer/school/parental ledgers remain eligible. Nora is divorced/woman/parent/sole carer, so the single-parent mock filter allows applying; Theo is divorced/man/parent with shared care, so it does not. Noah is married/man with no current children; paternity is allowed to apply without a future event, maternity/prenatal are unavailable. Sam has no dependent children, so child-dependent types are unavailable. Ella's unspecified profile produces To confirm. Iris's existing study ledger stays eligible. These values are public fiction, not inferred identities or approved legal decisions.

**Verification gates:** all response decisions match the schema and catalogue IDs; identities/policy versions agree; unknown/missing/type/company/account cases fail closed; no eligibility object appears in shared availability; submitted/tampered disabled types cannot finish a mock preview. Real API tests must deny company A reading or submitting for company B (including guessed employee/event IDs), reject stale/revoked policy decisions, and verify account cache separation. The public fixture bundle cannot prove tenant isolation.
