# API contract

Status: founder-authorized fictional implementation · 2026-10-27 · [VAC-13](../jira/VAC-13-api-backed-settings.md).

The Functions host serves `/api/users`, `/api/organizations` and `/api/auth/sessions`. Application services and typed domain aggregates follow [ADR-0003](../adr/0003-domain-and-application-services.md). Set `DevelopmentAuthentication__Enabled=true` and `SeedData__Enabled=true` explicitly for local/test sign-in and fictional data; both default off. The resource endpoints always use the same application services. The existing health endpoint remains independent. Only fictional data belongs here. All twelve fictional accounts remain seeded on the server with the same account/membership GUIDs as the schema examples. In default InMemory mode, runtime edits live in one server process and reset on API restart; browser reload and sign-out retain edits. Accepted ADR-0004 adds opt-in SqlServer resource persistence under VAC-26, preserving these projections and routes. SQL resource edits can be durable, while sessions remain process-local and development-only. A repository swap does not implement production OpenID or reliable multi-worker sessions.

The [OpenAPI 3.0 specification](openapi.yaml) lists every path and HTTP method separately. Each operation is a separately indexed Azure Function trigger; no resource uses a catch-all route. The OpenAPI document is checked into `docs/` only; no Swagger UI or runtime OpenAPI endpoint is enabled.

Import the [Postman collection](vacate-api.postman_collection.json) to try all 42 operations with example JSON bodies and basic response tests. Set `baseUrl` if the local Functions host uses another address, run **Sign in** first, and let its test save the bearer token. The remaining collection variables use fictional seed GUIDs. Create requests capture IDs for related examples; soft-delete requests and sign-out are grouped last. Review the target URL before sending any cleanup request. These public development credentials and fixtures are local/demo-only, not production authentication.

`POST /auth/sessions` accepts `{ "username": "maya", "password": "maya" }` (the other firstname pairs, user/user and admin/admin remain available). It returns a random opaque bearer accessToken, expiresAt (eight hours), and a display person. Send `Authorization: Bearer <accessToken>` on every subsequent request. Browser fixture IDs and client-supplied roles are never authorization. `GET /auth/sessions/current` returns own profile plus current display membership; `DELETE /auth/sessions/current` revokes that token. Deleted/disabled accounts immediately lose authenticated access; removed memberships immediately lose company authorization. Public development credentials and browser session storage are for fiction only; production issuer/subject mapping, token validation, invitations and credential flows remain open in ADR-0002.

Paths below are relative to `/api`. Every entity has numeric `id` and immutable `guid`; numeric IDs are storage keys and domain foreign keys. Public item paths and relationship references use GUIDs, including company, role, department, team, manager and schedule references. Numeric route IDs are rejected. GUIDs are resolved server-side before authorization and mutation; usernames are never update targets. POST creates return 201/Location, PATCH returns the updated projection, DELETE returns 204. Read/write failures return `{ "error": "..." }` with 400 validation, 401 session, 403 forbidden, 404 unavailable/foreign, 409 conflict, 413 oversized or 415 media type. JSON payloads are bounded to 32 KiB. Unsupported/server-owned fields fail atomically. Responses use `Cache-Control: no-store`; errors do not log request payloads.

| Resource | Read | Create (API only) | Update | Delete (API only) |
|---|---|---|---|---|
| Account | `GET /users` company directory; `GET /users/{guid}` own private record or authorized colleague projection | `POST /users` admin, username/firstName/lastName; optional profile fields and companyId invite scope | `PATCH /users/{guid}` self profile allowlist; `PATCH /users/{guid}/account` admin username/status | `DELETE /users/{guid}` target-company admin |
| Membership | Own record under session/profile; admin `GET /organizations/{organizationGuid}/memberships[/{userGuid}]` | `POST /organizations/{organizationGuid}/memberships/{userGuid}` | `PATCH /organizations/{organizationGuid}/memberships/{userGuid}` admin | `DELETE /organizations/{organizationGuid}/memberships/{userGuid}` admin |
| Organization | Admin `GET /organizations[/{organizationGuid}]`; own membership `GET /organizations/{organizationGuid}/summary` | `POST /organizations` existing administrator | `PATCH /organizations/{organizationGuid}` admin name/workWeekDays and vacation settings below | `DELETE /organizations/{organizationGuid}` admin, empty organization only |
| Department | Admin or permitted scoped lead `GET /organizations/{organizationGuid}/departments[/{nodeGuid}]` | `POST /organizations/{organizationGuid}/departments` name | `PATCH /organizations/{organizationGuid}/departments/{nodeGuid}` admin name; scoped lead/admin approval override | `DELETE /organizations/{organizationGuid}/departments/{nodeGuid}` unreferenced only |
| Team | Admin or permitted scoped lead `GET /organizations/{organizationGuid}/teams[/{nodeGuid}]` | `POST /organizations/{organizationGuid}/teams` name, optional nullable departmentId | `PATCH /organizations/{organizationGuid}/teams/{nodeGuid}` admin name/departmentId; scoped lead/admin approval override | `DELETE /organizations/{organizationGuid}/teams/{nodeGuid}` unreferenced only |

Append `/deletion-request` and POST `{}` to an account, membership, organization, department or team item URI to record a request without deleting. No create/delete buttons are exposed in the web. The web edits personal profile, admin membership configuration, organization name/workweek and department/team names through HTTP. Membership creation is the fictional administrator invitation-assignment seam; it does not send invitations or simulate employee acceptance. Newly API-created accounts have no demo password; only seeded fictional personas can sign in. They are available for CRUD/access tests, not a complete account onboarding flow.

Self-profile PATCH accepts only firstName, middleName, lastName, gender, married, dependentChildren and soleCare. Omitted PATCH fields remain unchanged. Family defaults false/0/false apply on creation or explicit unknown/null normalization. Married plus soleCare is rejected. Colleague responses select only username, email, names, gender, jobTitle and systemRole; even admins do not read other accounts' family data. An authorized unassigned invitee has null jobTitle/systemRole. Admin membership responses include only employment/membership data and the display person, not family facts.

Membership PATCH accepts systemRoleId, jobRoleId, departmentId, teamId, managerUserId, hireDate, employmentEndDate, priorService, workScheduleId, holidayCalendarId, leavePolicyId and customAllocation. Company is immutable. Validate roles and structural/manager references in the target company. Membership belongs directly to the organization; department/team are optional and teams can be direct. A team and explicit department must agree. Dates use yyyy-MM-dd; priorService is non-negative fractional years. Derived balances and policyMinimum cannot be written, including by admins. No experience policy is configured: customAllocation remains provisional, while allocation and available stay null. An available trusted policy minimum must be met. No legal policy values are inferred. The separate reference leave ledger is unchanged by these configuration edits.

ASSUMPTION (development engineering scope): existing admins may create fictional unassigned accounts in an organization they administer and provision empty organizations. The creator receives an explicit development provisioning grant for that organization, without transferring their single membership. New organizations receive a default Member job role; `GET /organizations/{organizationGuid}/roles` lists company job roles and employee/admin system-role GUIDs. Only invitees created in the target company scope (or its removed members) may be assigned; this avoids arbitrary account claiming. Last-active-admin deletion/demotion/disable is rejected. Production organization provisioning and invitation authority remain OPEN QUESTIONS.

Account, membership, organization, department and team records have server-owned createdAt and updatedAt UTC instants; deleteRequestedAt and deletedAt start null. A request sets deleteRequestedAt but leaves the record accessible; DELETE sets deletedAt and also records a request if none exists. Soft-deleted records are excluded from normal reads and mutation; duplicate usernames stay reserved. Dependent references block structural deletion; no silent cascade/move. Account deletion also soft-deletes its membership. Reassigned memberships retain the old tombstone in process-local history. These columns are lifecycle evidence, not an immutable audit log or GDPR erasure. Retention, legal bases, erasure/export and request verification are undecided; do not use real personal data. Balance is a dated derived snapshot, not a separate lifecycle entity.

API requests serialize mutations within a single process. PATCH touches only supplied fields; there is no optimistic concurrency/ETag yet, so the latest accepted write wins for the same field. The web checks its originating actor/session before applying responses and does not silently fall back to local writes. Independent privacy/security review and production architecture remain required before real-data release.

### Delegated settings and vacation configuration · 2026-10-30

Organization records add `settings` with `requireVacationApproval`, `departmentLeadSettingsEnabled`, `teamLeadSettingsEnabled`, `carryoverEnabled` and `carryoverYears`. Organization PATCH accepts those fields at the top level alongside name/workWeekDays. The four switches require non-null booleans; years requires a non-negative integer. Omission preserves the stored value. Invalid/null/unknown fields reject the entire patch. Organization owners/HR and existing authorized administrators can edit them; employees and leads cannot self-grant delegation.

Department/team records add nullable `requireVacationApproval`. Item PATCH accepts true, false or null (inherit). The effective rule is the first explicit value in **team → department → organization** order; false is an override. New organizations default to approval required, delegation disabled and carryover disabled with zero years. The fictional organization explicitly enables both lead delegation switches. Carryover is saved configuration only: zero means unlimited years when enabled; no transfer, expiry, balance changes or processing runs from it.

The own-organization summary adds `settingsAccess`: `role`, `organization` (boolean), `effectiveVacationApproval` (boolean), and filtered `departments`/`teams` arrays of permitted nodes. A server-owned membership SettingsRole distinguishes Employee, TeamLead, DepartmentLead, Owner and HR without changing employee/admin system-role or job-title contracts. It is not accepted by public account/membership PATCH. Seeded assignments are Leah/TeamLead, Ella/DepartmentLead, Nora/Owner and Daria/HR. Owner/HR require admin system role and lose that settings designation on demotion; existing admin privileges remain compatible.

With delegation enabled, a team lead can read/update only their assigned team's approval override. A department lead can read/update only their assigned department and its actual child teams. Lists and summary arrays are filtered on the server. A lead cannot rename, reparent, create or delete structure. Revoked delegation, removed membership, stale/foreign node or foreign organization denies the read/write (404); no session returns 401. Profile/System remain available without management access. Every mutation retains server-owned UTC timestamps; node changes also touch their organization. No new endpoint or lifecycle entity is introduced.

Membership annual balance projections preserve pending separately and deduct it from available only when effective vacation approval is off. Unknown policy/allocation remains null. My Leave presents the existing explicitly fictional own ledger, recurring fixed-type balances used in the reference year and descending dated requests; event-based types remain in history. It does not turn reference records into authoritative API requests. The Approval Requests inbox remains unavailable; assignment, submission and decisions are outside this change.

## Leave request creation · VAC-31

Implementation scope: own-member whole-day preview/submission/history only, plus organization `timeZone` (default `UTC`) and nullable `countryCode`. The organization timezone determines the server's current calendar date for past-date classification; it does not change frontend date display or date-only values. Department/team/organization approval precedence is unchanged. Future-date approval decisions, cancellation permissions, automatic policy grants and client timezone conversion are deferred.

Own-member routes (the organization GUID must be the authenticated actor's active company; no employee/membership target can be supplied):

| Method | Path | Result |
|---|---|---|
| POST | `/organizations/{organizationId}/leave/preview` | Authoritative date/charge/balance preview, warnings and validation errors |
| POST | `/organizations/{organizationId}/leave/requests` | Create only uncovered working dates, or acknowledge already-covered selection; idempotency key required |
| GET | `/organizations/{organizationId}/leave/requests` | Own saved request history with actual UTC creation timestamp and included date states |
| GET | `/organizations/{organizationId}/leave/calendar` | Own saved per-date projection; no new colleague leave-detail access |

Preview input contains `leaveTypeId`, `unit` (`days` or unsupported `hours`), `mode` (`duration` or `range`), `startDate` (ISO date-only), and either positive integer `duration` or inclusive `endDate`. Submission also supplies an `idempotencyKey` UUID and may send the preceding preview's `fingerprint` as `previewFingerprint`. A changed authoritative preview returns 409 so the client refreshes it for review/reconfirmation. Unsupported/server-owned identity/state/charge fields are rejected. No client-calculated amount is authoritative.

The preview reports included working dates, excluded dates/reasons, already-covered dates, newly chargeable dates, per-type/year balances, warnings/errors and whether submission is allowed. Only the selected type's finite configured period balances may fund leave. Missing type/year allocation is a configuration error, never zero/unlimited or an automatically synthesized statutory grant. An explicit current-period custom allowance can fund requests even while the separate statutory policy floor is unresolved; absent that, an evaluated policy amount is required. This does not change the legacy policy-derived balance projection or invent policy defaults. Existing current-period annual inputs do not become grants for every year.

Working dates use Monday–Friday or Monday–Saturday according to organization workweek; applicable stored country public holidays are excluded. Missing holiday coverage falls back to the working schedule/weekends with an explanatory warning. Excluded dates are not persisted as leave occurrences. Duration derives an end date by counting working dates inclusively; overlaps do not extend the range to replace dates.

Past dates (strictly before today in the organization's configured timezone) warn and bypass approval. Today/future dates follow the effective approval setting. Pending dates remain distinct from remaining balance and do not consume it while approval is required. Every new charged date uses eligible previous-year annual leftovers first through 31 March inclusive for Greece, then its leave-year allowance; no borrowing from later years. Reject a negative result for any applicable period. Existing used/pending totals remain derived; membership allowance is not decremented.

Pending/approved existing leave covers a date regardless of selected type; cancelled/rejected leave does not. Warn, preserve original type/status, and create only uncovered dates. Fully covered selections return an already-covered acknowledgement without new request/occurrence/charge rows; zero working-date selections are invalid. Retries and concurrent submissions cannot double-charge a day. Idempotency keys are scoped to actor/company and may not be reused for a different payload. Revoke access/tenant mismatch is checked before reads, previews, mutations or replay responses.

Organization settings retain the existing admin/delegation authorization boundaries. `countryCode` is optional ISO country configuration (unknown does not default every organization to Greece); `timeZone` is a validated timezone identifier, default UTC, with existing records backfilled. For GR, the annual carryover use deadline is read-only policy information; attempts to override it are rejected rather than changing the policy. The setting does not authorize automatic entitlement expiry/payroll settlement. Organization modifications retain server-owned UTC lifecycle timestamps.
