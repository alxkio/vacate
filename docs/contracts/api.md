# API contract

Status: founder-authorized fictional implementation · 2026-10-27 · [VAC-13](../jira/VAC-13-api-backed-settings.md).

The Functions host serves `/api/users`, `/api/organizations` and `/api/auth/sessions`. Application services and typed domain aggregates follow [ADR-0003](../adr/0003-domain-and-application-services.md). SQL development sign-in requires `DevelopmentAuthentication__Enabled=true` plus explicitly saved test-account login grants. Disposable local accounts require the non-publishable [test host build](../../api/testing/README.md); ordinary InMemory hosting starts empty. The resource endpoints always use the same application services. The existing health endpoint remains independent. Only fictional data belongs here. The twelve automated-test accounts retain the account/membership GUIDs in the schema examples; published builds do not embed or create them. In default InMemory mode, runtime edits and sessions live in one server process and reset on API restart; browser reload and sign-out retain resource edits. Accepted ADR-0004 adds opt-in SqlServer resource persistence under VAC-26 and shared hashed sessions under the 2026-11-13 VAC-42 amendment, preserving these projections and routes. Shared sessions support upgraded instances using the same migrated SQL database; development sign-in remains fictional and does not implement production OpenID.

The [OpenAPI 3.0 specification](openapi.yaml) lists every path and HTTP method separately. Each operation is a separately indexed Azure Function trigger; no resource uses a catch-all route. The OpenAPI document is checked into `docs/` only; no Swagger UI or runtime OpenAPI endpoint is enabled.

Import the [Postman collection](vacate-api.postman_collection.json) to try all 42 operations with example JSON bodies and basic response tests. Set `baseUrl` if the local Functions host uses another address, run **Sign in** first, and let its test save the bearer token. The remaining collection variables use fictional seed GUIDs. Create requests capture IDs for related examples; soft-delete requests and sign-out are grouped last. Review the target URL before sending any cleanup request. These public development credentials and fixtures are local/demo-only, not production authentication.

`POST /auth/sessions` accepts `{ "username": "maya", "password": "maya" }` (the other firstname pairs, user/user and admin/admin remain available). It returns a random opaque bearer accessToken, expiresAt (30 minutes after issuance, absolute expiry; API activity does not extend it), and a display person. Send `Authorization: Bearer <accessToken>` on every subsequent request. Browser fixture IDs and client-supplied roles are never authorization. `GET /auth/sessions/current` returns own profile plus current display membership; `DELETE /auth/sessions/current` revokes that token. Deleted/disabled accounts immediately lose authenticated access; removed memberships immediately lose company authorization. Public development credentials and browser session storage are for fiction only; production issuer/subject mapping, token validation, invitations and credential flows remain open in ADR-0002.

In SqlServer mode, only a hash of the opaque ticket is persisted with its global account reference and server-owned creation/expiry instants. Session rows do not cache tenant permissions. Logout removes only the selected ticket; disabling/deleting an account revokes all its tickets. Invalid, expired or revoked tickets return 401. Database failures must not masquerade as 401; the web retains its saved ticket during recoverable server/network failures, hides incomplete private state and offers retry. The HTTP payloads and Angular calls are unchanged by the storage adapter. Upgrading from memory sessions requires one new sign-in because old tickets cannot be imported. Database/cross-instance execution evidence is recorded separately from InMemory HTTP checks.

Paths below are relative to `/api`. Every entity has numeric `id` and immutable `guid`; numeric IDs are storage keys and domain foreign keys. Public item paths and relationship references use GUIDs, including company, role, department, team, manager and schedule references. Numeric route IDs are rejected. GUIDs are resolved server-side before authorization and mutation; usernames are never update targets. POST creates return 201/Location, PATCH returns the updated projection, DELETE returns 204. Read/write failures return `{ "error": "..." }` with 400 validation, 401 session, 403 forbidden, 404 unavailable/foreign, 409 conflict, 413 oversized or 415 media type. JSON payloads are bounded to 32 KiB. Unsupported/server-owned fields fail atomically. Responses use `Cache-Control: no-store`; errors do not log request payloads.

Append `/deletion-request` and POST `{}` to an account, membership, organization, department or team item URI to record a request without deleting. No create/delete buttons are exposed in the web. The web edits personal profile, admin membership configuration, organization name/workweek and department/team names through HTTP. Membership creation is the fictional administrator invitation-assignment seam; it does not send invitations or simulate employee acceptance. Newly API-created accounts have no demo password; only seeded fictional personas can sign in. They are available for CRUD/access tests, not a complete account onboarding flow.

Self-profile PATCH accepts only firstName, middleName, lastName, gender, married, dependentChildren and soleCare. Omitted PATCH fields remain unchanged. Family defaults false/0/false apply on creation or explicit unknown/null normalization. Married plus soleCare is rejected. Colleague responses select only username, email, names, gender, jobTitle and systemRole; even admins do not read other accounts' family data. An authorized unassigned invitee has null jobTitle/systemRole. Admin membership responses include only employment/membership data and the display person, not family facts.

Membership PATCH accepts systemRoleId, jobRoleId, departmentId, teamId, managerUserId, hireDate, employmentEndDate, priorService, workScheduleId, holidayCalendarId, leavePolicyId and customAllocation. Company is immutable. Validate roles and structural/manager references in the target company. Membership belongs directly to the organization; department/team are optional and teams can be direct. A team and explicit department must agree. Dates use yyyy-MM-dd; priorService is non-negative fractional years. Derived balances and policyMinimum cannot be written, including by admins. No experience policy is configured: customAllocation remains provisional, while allocation and available stay null. An available trusted policy minimum must be met. No legal policy values are inferred. The separate reference leave ledger is unchanged by these configuration edits.

ASSUMPTION (development engineering scope): existing admins may create fictional unassigned accounts in an organization they administer and provision empty organizations. The creator receives an explicit development provisioning grant for that organization, without transferring their single membership. New organizations receive a default Member job role; `GET /organizations/{organizationGuid}/roles` lists company job roles and employee/admin system-role GUIDs. Only invitees created in the target company scope (or its removed members) may be assigned; this avoids arbitrary account claiming. Last-active-admin deletion/demotion/disable is rejected. Production organization provisioning and invitation authority remain OPEN QUESTIONS.

Account, membership, organization, department and team records have server-owned createdAt and updatedAt UTC instants; deleteRequestedAt and deletedAt start null. A request sets deleteRequestedAt but leaves the record accessible; DELETE sets deletedAt and also records a request if none exists. Soft-deleted records are excluded from normal reads and mutation; duplicate usernames stay reserved. Dependent references block structural deletion; no silent cascade/move. Account deletion also soft-deletes its membership. Reassigned memberships retain the old tombstone in process-local history. These columns are lifecycle evidence, not an immutable audit log or GDPR erasure. Retention, legal bases, erasure/export and request verification are undecided; do not use real personal data. Balance is a dated derived snapshot, not a separate lifecycle entity.

API requests serialize mutations within a single process. PATCH touches only supplied fields; there is no optimistic concurrency/ETag yet, so the latest accepted write wins for the same field. The web checks its originating actor/session before applying responses and does not silently fall back to local writes. Independent privacy/security review and production architecture remain required before real-data release.

### Delegated settings and vacation configuration · 2026-10-30

Organization records add `settings` with `requireVacationApproval`, `departmentLeadSettingsEnabled`, `teamLeadSettingsEnabled`, `carryoverEnabled` and `carryoverYears`. Organization PATCH accepts those fields at the top level alongside name/workWeekDays. The four switches require non-null booleans; years requires a non-negative integer. Omission preserves the stored value. Invalid/null/unknown fields reject the entire patch. Organization owners/HR and existing authorized administrators can edit them; employees and leads cannot self-grant delegation.

Department/team records add nullable `requireVacationApproval`. Item PATCH accepts true, false or null (inherit). The effective rule is the first explicit value in **team → department → organization** order; false is an override. New organizations default to approval required, delegation disabled and carryover disabled with zero years. The fictional organization explicitly enables both lead delegation switches. Carryover is saved configuration only: zero means unlimited years when enabled; no transfer, expiry, balance changes or processing runs from it.

The own-organization summary adds `settingsAccess`: `role`, `organization` (boolean), `effectiveVacationApproval` (boolean), and filtered `departments`/`teams` arrays of permitted nodes. A server-owned membership SettingsRole distinguishes Employee, TeamLead, DepartmentLead, Owner and HR without changing employee/admin system-role or job-title contracts. It is not accepted by public account/membership PATCH. Seeded assignments are Leah/TeamLead, Ella/DepartmentLead, Nora/Owner and Daria/HR. Owner/HR require admin system role and lose that settings designation on demotion; existing admin privileges remain compatible.

With delegation enabled, a team lead can read/update only their assigned team's approval override. A department lead can read/update only their assigned department and its actual child teams. Lists and summary arrays are filtered on the server. A lead cannot rename, reparent, create or delete structure. Revoked delegation, removed membership, stale/foreign node or foreign organization denies the read/write (404); no session returns 401. Profile/System remain available without management access. Membership annual balance projections preserve pending separately and deduct it from available only when effective vacation approval is off. Unknown policy/allocation remains null. ## Leave request creation · VAC-31

Implementation scope: own-member whole-day preview/submission/history only, plus organization `timeZone` (default `UTC`) and nullable `countryCode`. The organization timezone determines the server's current calendar date for past-date classification; it does not change frontend date display or date-only values. Department/team/organization approval precedence is unchanged. Future-date approval decisions, cancellation permissions, automatic policy grants and client timezone conversion are deferred.

Own-member routes (the organization GUID must be the authenticated actor's active company; no employee/membership target can be supplied):

| Method | Path | Result |
|---|---|---|
| POST | `/organizations/{organizationId}/leave/preview` | Authoritative date/charge/balance preview, warnings and validation errors |
| POST | `/organizations/{organizationId}/leave/requests` | Create only uncovered working dates, or acknowledge already-covered selection; idempotency key required |
| GET | `/organizations/{organizationId}/leave/requests` | Own saved request history with actual UTC creation timestamp and included date states |
| GET | `/organizations/{organizationId}/leave/calendar` | Own saved per-date projection; no new colleague leave-detail access |

Preview input contains `leaveTypeId`, `unit` (`days` or unsupported `hours`), `mode` (`duration` or `range`), `startDate` (ISO date-only), and either positive integer `duration` or inclusive `endDate`. Submission also supplies an `idempotencyKey` UUID and may send the preceding preview's `fingerprint` as `previewFingerprint`. A changed authoritative preview returns 409 so the client refreshes it for review/reconfirmation. Unsupported/server-owned identity/state/charge fields are rejected. No client-calculated amount is authoritative.

The preview reports included working dates, excluded dates/reasons, already-covered dates, newly chargeable dates, per-type/year balances, warnings/errors and whether submission is allowed. Only the selected type's finite configured period balances may fund leave. Missing type/year allocation is a configuration error, never zero/unlimited or an automatically synthesized statutory grant. An explicit current-period custom allowance can fund requests even while the separate statutory policy floor is unresolved; absent that, an evaluated policy amount is required. This does not change the legacy policy-derived balance projection or invent policy defaults. Existing current-period annual inputs do not become grants for every year.

Working dates use Monday–Friday or Monday–Saturday according to organization workweek; applicable stored country public holidays are excluded. Missing holiday coverage falls back to the working schedule/weekends with an explanatory warning. Excluded dates are not persisted as leave occurrences. Duration derives an end date by counting working dates inclusively; overlaps do not extend the range to replace dates.

Past dates (strictly before today in the organization's configured timezone) warn and bypass approval. Today/future dates follow the effective approval setting. Pending dates remain distinct from remaining balance and do not consume it while approval is required. Every new charged date uses eligible previous-year annual leftovers first through 31 March inclusive for Greece, then its leave-year allowance; no borrowing from later years. Reject a negative result for any applicable period. Existing used/pending totals remain derived; membership allowance is not decremented.

Pending/approved existing leave covers a date regardless of selected type; cancelled/rejected leave does not. Warn, preserve original type/status, and create only uncovered dates. Fully covered selections return an already-covered acknowledgement without new request/occurrence/charge rows; zero working-date selections are invalid. Retries and concurrent submissions cannot double-charge a day. Idempotency keys are scoped to actor/company and may not be reused for a different payload. Revoke access/tenant mismatch is checked before reads, previews, mutations or replay responses.

Organization settings retain the existing admin/delegation authorization boundaries. `countryCode` is optional ISO country configuration (unknown does not default every organization to Greece); `timeZone` is a validated timezone identifier, default UTC, with existing records backfilled. For GR, the annual carryover use deadline is read-only policy information; attempts to override it are rejected rather than changing the policy. The setting does not authorize automatic entitlement expiry/payroll settlement. Organization modifications retain server-owned UTC lifecycle timestamps.

## Company administration · VAC-43 · 2026-11-12

This owner-authorized extension supersedes the earlier statements that actual approval decisions are unavailable. All routes below require a bearer session. Administration requires an active company administrator; a configured approver must also be an active administrator in that company. Public GUIDs never grant access by themselves. Foreign-company and unauthorized administrative resources return 404; expired sessions return 401. Mutations accept only their documented fields, require JSON (including PUT), and return 400 validation, 409 conflict, 413 oversized-body or 415 unsupported-content-type errors through the existing `{error: string}` envelope.

| Method | Path under `/organizations/{organizationId}` | Result |
|---|---|---|
| GET | `/admin/calendar` | `{holidays, closures, approvers, candidates}`; administrative reports/configuration only |
| GET | `/leave/company-calendar` | Member-safe `{holidays, closures}`; closure summaries omit employee results, assignment and balances |
| POST | `/admin/holidays` | Add `{name, month, day}` fixed recurring company holiday |
| PUT | `/admin/approvers` | Set/clear `{scope, scopeGuid, approverGuid}`; returns current administrative calendar |
| POST | `/admin/closures/preview` | Review `{name, startDate, endDate, deductAnnualLeave}`; returns draft plus employee `results` |
| POST | `/admin/closures` | Publish the same closure draft plus required UUID `idempotencyKey`; returns persisted closure/results |
| GET | `/admin/approvals` | Only requests currently assigned to the authenticated administrator and containing Pending dates |
| POST | `/admin/approvals/{requestId}/decision` | `{decision: "approve" | "decline"}`; updated assigned request |
| GET | `/admin/personnel?year=2026` | Sanitized personnel/annual totals and actual saved dated requests for that calendar year |

Holidays are whole-company named month/day recurrences. February 29 applies only in leap years; no weekend substitution is inferred. They are combined with country holidays for fresh preview/closure working-date selection, without duplicate dates or rewriting already-saved requests. Missing national coverage still produces the existing schedule-fallback warning. No regional examples are seeded as legal facts. Holiday responses include `guid`, `name`, `month`, `day`, UTC `createdAt`/`updatedAt`, and nullable `deleteRequestedAt`/`deletedAt`. Creation is supported; editing/removal/correction semantics remain outside this implementation.

Approver `scope` is `organization`, `department` or `team`; `scopeGuid` identifies the same-company scope (organization scope uses the company GUID). Nullable `approverGuid` clears the explicit setting. Effective assignment is team → department → organization; it is unrelated to job title, manager or settings delegation. An explicitly assigned administrator may decide their own request. Changing assignment reroutes **all pending requests**, including legacy pending records; approved/declined records and their completed decision attribution remain unchanged. A missing or inactive administrator gives an actionable configuration error for new approval-required dates; past-only approval-bypass requests still work. Configure a valid approver to recover unassigned/stale pending requests. Permission and effective membership scope are rechecked at every inbox/decision request; the former approver loses access after rerouting or a membership move changes effective assignment. `candidates` contains only active company administrators as `{guid, displayName}`.

An approval request response is `{requestGuid, userGuid, displayName, leaveTypeId, createdAt, dates, approverGuid, decidedAt}`. The server updates only Pending dates; already-approved past dates are preserved on both approval and decline. Declined dates release their pending coverage. Approval rechecks finite per-type/entitlement-year balance and rejects insufficient/unknown funding atomically, leaving the request pending. Concurrent/retried completed decisions return 409; they never charge twice. Own saved request records additionally expose nullable `approverGuid`, nullable UTC `decidedAt`, `source` (`EmployeeRequest` or `CompanyClosure`), nullable `closureGuid`, and nullable `updatedAt` for backward compatibility; new records set it. Per-date `status` now includes `Declined`. Own calendar continues to expose Approved/Pending dates only.

Publishing closures automatically records approved leave for active company members on applicable company working dates, constrained by known hire/end dates. Missing employment boundaries are unbounded; unknown annual funding remains unknown. `deductAnnualLeave: true` charges annual leave, with existing Greek carryover-date allocation rules; false uses distinct `company-closure` records and leaves balances unchanged. Existing Approved/Pending leave of any type is preserved and not duplicated. Insufficient/unknown funding skips that employee's entire closure range and explicitly reports them; other employees may receive records as the owner authorized. Publication is transactional for the final planned set, idempotent per company/key, and has no ordinary employee-approval step. Closures spanning more than 366 elapsed days are rejected. Preview is advisory; publish recalculates authoritative eligibility/overlap/funding and returns the actual report. Already published leave is not retroactively rewritten by later calendar configuration.

Closure responses include `guid`, draft fields, UTC lifecycle timestamps, publication `idempotencyKey`, and `results: [{userGuid, displayName, outcome, days, reason}]`. Outcomes are `recorded`, `skipped` and `already-covered`. The latter means actual applicable dates were already covered; no applicable working/employment dates yields `skipped` with a reason. No-deduction provenance remains visible in own history/calendar and admin reporting. Editing, revocation and retrospective correction are not exposed.

Personnel rows are `{userGuid, displayName, departmentName, teamName, year, allocation, used, pending, available, openingUsed, requests}`. Annual totals use entitlement year, while the included request dates use the selected calendar year; carryover may therefore cross these boundaries. Null allocation/available remains unknown. `openingUsed` explicitly distinguishes undated imported consumption from dated actual request records. Pending and declined states are visible in dated history but are not approved consumption. No private family/profile/medical inputs, request notes or exports are included. The sanitized employee directory is unchanged.

Persistence uses normalized company-keyed `CompanyHolidays`, `CompanyClosures`, `CompanyClosureResults`, `CompanyApproverAssignments`, plus leave-request decision/provenance columns. UTC lifecycle constraints, rowversion for new configuration records, unique publication/active-assignment keys and the existing transaction admission/company locks protect concurrent writes. The operator-owned forward migration and runtime grants must run before application publication; startup never migrates. Runtime can update Leaves/LeaveRequests for decisions while DELETE, schema/migration writes remain ungranted. No live database migration or deployment is implied by source/offline verification.

## Permanent personal-request deletion · owner decision · 2026-11-13

`DELETE /organizations/{organizationId}/leave/requests/{requestId}` permanently removes a saved **personal** leave request and its associated dated charges/history. An authenticated, current active company administrator is required, including when deleting their own request. An employee, a demoted administrator retaining only a provisioning grant, a foreign-company actor or guessed/unknown request GUID receives 404; an expired/missing session receives 401. No employee target, deletion flag or client-calculated adjustment is accepted. This is a real resource operation, not a test-only cleanup endpoint, and does not add a web deletion control.

Success is **204 No Content**. Removal is atomic under the existing unit-of-work/SQL admission locks. Approved annual charges are removed from derived used consumption, pending dates from pending totals, while declined dates and imported opening consumption are not charged/reversed again. Every entitlement year and leave type is restored from its own removed records; allowances and other requests remain unchanged. Saved history, own calendar and assigned inbox no longer include the request. A second or concurrent losing DELETE returns 404 and cannot restore balance twice.

Generated company-closure leave is protected: any request with closure provenance returns **409**, regardless of whether its balance impact was annual or none. Closure publication/cancellation policy remains separate. The request's original submission-key row is removed together with it; a later authorized POST using that key is a fresh submission with a new request GUID, never a replay of the deleted request. Covered-only acknowledgment receipts are separate records and cannot return a deleted request GUID. If replay finds previously covered dates are now uncovered, it returns 409 with guidance to review and use a new submission key, rather than falsely reporting those dates as still covered.

SQL runtime grants add physical DELETE only on `Leaves` and `LeaveRequests`; existing physical-delete denials on users, company configuration and covered receipts remain. The operator verifies those boundaries and must refresh grants before a SQL-backed API uses this endpoint. No schema migration is needed, and no live database grant/application is implied by source or InMemory checks. This operation removes the selected leave resource; it is not an account deletion or a claim of complete personal-data erasure.

## Employee cancellation and expiry · VAC-42 · 2026-11-14

`POST /organizations/{organizationId}/leave/requests/{requestId}/cancel` takes `{dates: [ISO-date, ...]}` and returns the updated own `LeaveRequest`. Requires an active same-company member owning that personal request. Unknown/foreign request/member/company returns 404; generated closures, empty/duplicate/unknown dates, past dates or non-active statuses return 409. The entire selection is validated before mutation. Clients must refresh before relying on this hint; the mutation checks current state again. Own calendar includes active Approved/Pending dates only. Admin-only permanent DELETE permissions are unchanged.

On access Pending dates before company-local today transition to Expired, atomically releasing dated pending totals and calendar/overlap coverage. Mixed requests retain future Pending dates; approval can decide only those remaining active dates. Cancelled and Expired are added to public status values.
